# Why the linter is configured the way it is

Rules switched off here are ones that are wrong about this codebase, not ones
that were inconvenient. Each is listed with the reason, so a future change that
invalidates the reason can put the rule back.

**react/react-in-jsx-scope** — the automatic JSX runtime is in use
(`jsx: react-jsx`), so React is correctly never named in a file that renders.

**unicorn/prefer-add-event-listener** — the `onload`/`onerror` assignments it
finds are on throwaway elements built to measure one file. One handler, torn
down with the element; a listener would be more code for nothing.

**unicorn/no-array-sort** — flags `sort()` as mutating. Every use here sorts the
array `filter()` just returned, which nothing else holds a reference to.

**unicorn/require-post-message-target-origin** — a false positive. The call it
finds is `Client.postMessage` in the service worker, whose second argument is a
transfer list, not an origin; only `window.postMessage` takes one. The loop
around it already checks the client's origin.

**no-unmodified-loop-condition** — a false positive in `greeting.ts`. The
condition also reads `deck`, which is reassigned each pass, and a `tries < 8`
counter bounds it regardless.

**no-await-in-loop** — the loops it finds drain the outbox and walk export
pages, both of which must stay sequential.

## Advisory rather than blocking

**react/set-state-in-effect** and **react/refs** are left as warnings. Every
current instance is a legitimate pattern: state set inside an async loader after
an await, a latest-value ref written during render, or a one-shot branch when no
project is configured. They stay switched on because the same rules do catch
real cascading renders, and the warnings should be read rather than assumed.
